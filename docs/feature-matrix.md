# 能力矩阵与取舍

> 这份文件回答一个问题：**同类工具都有的能力里，我们缺哪些、该补哪些、哪些坚决不补。**
> 只按「能不能改变工作流」判，不按「功能清单看起来齐不齐」判 —— 见 `growth-plan.md` 第 8 条。

判断口径：

- **普遍具备**（九成以上的同类工具都有）→ 缺了就是短板，用户会在第一周撞到
- **部分具备**（约一半工具支持，或只在付费档里）→ 做了是差异点，不做也不算残废
- **少数具备**（一两家有，且多是重型工具）→ 只在能顺手做掉时才做
- 来源是各工具公开的功能页与文档的横向比对（2026-11 整理），**不点名**，避免把这份文件写成对标清单

## 1. 已经具备

| 能力 | 我们的做法 |
| --- | --- |
| HTTPS 解密 | 固定根证书 + 按域名动态签叶子证书，跨版本、跨形态复用 |
| HTTP/2 | 走 ALPN 真协商 h2，多路复用逐条记录，不只接受 h1 的降级 |
| 握手失败诊断 | 单独列出反复失败的域名，给原因，一键进「跳过解密」 |
| Mock / 本地响应替换 | 方法 + URL（包含 / 通配 / 正则）+ 域名匹配，可加延迟 |
| 断点（请求 + 响应） | 挂起后改方法 / URL / 头 / body / 状态码，60s 超时自动放行 |
| 重放 | 改任意字段重发，结果入列并与原请求关联 |
| 响应对比 | 重放 vs 原请求，JSON 按结构比、文本按行比 |
| 弱网 / 断网 / 超时 | 按规则命中，实时切断存量隧道 |
| 搜正文、按列排序 | 搜索范围可扩到 body；状态 / 耗时 / 大小可排序 |
| 会话（历史记录） | 清空留档、回看、改名、导出 HAR / JSON |
| HAR 导出 | HAR 1.2，含扩展字段，可直接给别的工具看 |
| 多语言、精简顶栏、命令面板 | ⌘K 既能搜请求也能执行命令 |

## 2. 普遍具备但我们缺 —— 必做

| 能力 | 为什么是短板 | 成本 | 批次 |
| --- | --- | --- | --- |
| **域名映射** | 「把线上域名指到本机 / 测试机」是联调每天都要做的事。没有它只能改客户端或改 hosts，且断点只能一条条改 URL | 低 | A |
| **导入 HAR** | 别人给的 HAR 打不开，等于半个协作链路断了。而且导入后能直接重放、对比 | 中 | A |
| **任意两条对比** | 现在的对比绑在「重放关系」上，但真实场景是「登录前后两次同一接口」。diff 引擎已有，只差入口 | 低 | A |
| **响应体另存 / 图片预览** | 抓到的图片、zip、pdf 现在只能看乱码，等于数据能看不能取 | 低 | A |
| **WebSocket 帧记录** | 即时通讯、推送、协同编辑类 App 全靠 WS，现在完全看不见 | 高 | B |
| **耗时分解** | 一个请求慢 3 秒，要能回答「慢在 DNS / 握手 / 服务端 / 下载」。只有总耗时等于让人猜 | 中 | B |
| **按接口聚合的性能视图** | 抓了几千条之后，需要「哪些接口在拖后腿」（P50 / P95 / 错误率 / 慢请求 Top） | 中 | B |

## 3. 部分具备 —— 做了是差异点

| 能力 | 判断 | 批次 |
| --- | --- | --- |
| **脚本规则**（用 JS 自动改请求 / 响应） | 重型工具的标志性能力，但也是「工具变平台」的起点。用 Node 的 `vm` 沙箱做，只给同步的 `onRequest / onResponse` 两个钩子，不开放网络与文件 | C |
| **自定义派生列**（JSONPath 取值成列） | 把 `data.items[0].id` 提成列表里的一列，排障时非常省眼。成本低、感知强 | C |
| **SSE 流式消息视图** | 现在只做流式转发，消息不拆条。做完能把「服务端推了几条、间隔多大」看清楚 | B |
| **条件告警**（匹配规则时提醒） | 等着某个错误码 / 某个字段出现时很有用，但容易做成噪音源，要先有静音策略 | C |
| **gRPC / Protobuf 解析** | 需要描述文件或反射，投入产出比取决于用户里 gRPC 的比例 | C（低优先） |

## 4. 明确不做

| 不做 | 理由 |
| --- | --- |
| **macOS 签名与公证** | 需要付费开发者账号与固定流水线，不是代码问题。文档里继续给 `xattr -cr` 的说明 |
| **HTTP/3（QUIC）解密** | 代理模式天然看不见 UDP 上的 QUIC；真做要接管 UDP + 自己做 QUIC 栈，Node 生态里没有能撑住的实现。目前策略是「看得见就记录握手失败，并引导降级」 |
| **免证书的网卡层抓包** | 要特权、要各平台分别写，等于第二个产品；而且和我们「零依赖、一条命令起服务」的定位冲突 |
| **透明代理 / 系统扩展** | 平台专属，且和我们「不签名、不装驱动」的取舍矛盾 |
| **证书固定（pinning）绕过** | 那是客户端侧的事，代理能做的只是「识别出来并告诉你」（已做） |
| **批量压测 / p99 尾延迟** | 有专门工具做得更好。我们提供性能视图（P50 / P95 / 慢请求 Top）就够，不承诺压测 |
| **脚本开放网络与文件** | 一旦开放，脚本就能把抓到的流量发出去，信任模型崩了。只给纯函数式钩子 |

## 5. 排期

| 批次 | 内容 | 主题 |
| --- | --- | --- |
| **A** | 域名映射、导入 HAR、任意两条对比、响应体另存 / 图片预览 | 补齐短板，都是「每天都会用到」的 |
| **B** | WebSocket 帧、耗时分解、性能视图、SSE 消息视图 | 从「能看」到「看得懂」 |
| **C** | 脚本规则、自定义派生列、条件告警、gRPC 视图 | 从工具到平台，按反馈热度决定顺序 |

每批都按同一套纪律走：先写自检，再写实现，全套回归绿了才发版；新增能力必须同时更新
`README(.zh-CN).md` 的能力表、`docs/api(.zh-CN).md` 的接口、以及 `docs/development(.zh-CN).md` 的自检清单。
