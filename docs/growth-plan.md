# 推广与反馈飞轮

> 目标不是「拉一波流量」，而是让**一条反馈能在几天内变成一个版本，再变成下一批用户**。
> 所有动作都围绕这条链路，不产生反馈的动作不做。

## 1. 只打三个差异点

抓包工具是红海，拼功能数量必输。对外只说这三件别人做不到或做不好的：

| 差异点 | 一句话 | 可信度来源 |
| --- | --- | --- |
| 零配置 | 装一次根证书，之后不用再管设备、端口、白名单 | 首次启动自动生成 CA + 一键安装命令 |
| HTTP/2 真解密 | 走 h2 的 App 不会静默降级成「安全透传」 | 详情面板直接标「协议版本 HTTP/2」 |
| 开源可审计 | 内网、金融、医疗场景敢用，能自己看代码 | MIT，纯 Node 内核无原生依赖 |

其余能力（Mock、弱网、断网、规则工作区）是**留住**人的理由，不是**吸引**人的理由，别放在首屏。

## 2. 人群与抓手

按信任成本排序，先打最信任你的人。

| 人群 | 他们的痛 | 给他的抓手 |
| --- | --- | --- |
| iOS / Flutter 开发 | 真机抓包要配代理 + 装证书，一个环节错就白屏 | 「iOS 真机 5 分钟」图文 + GIF |
| 测试 / QA | 发现问题后要「交出去」让人复现 | 导出 HAR、诊断包、失败原因判定 |
| 后端 / 联调 | 不知道客户端到底发了什么 | 规则工作区、Mock 命中、请求重放 |

## 3. 四周排期（每周只做一件事）

| 周 | 主任务 | 产出物 | 验收 |
| --- | --- | --- | --- |
| W1 | 地基 | README 首屏 GIF（15 秒走完抓一次请求）+ 三条安装命令 + Release notes 改写成「本版故事」 | 陌生人看完首屏能自己装上并抓到一条 |
| W2 | 深水区长文 | 《HTTP/2 在 MITM 里为什么会被静默降级》—— 讲 ALPN 协商与握手诊断的坑 | 掘金/知乎/V2EX 同步，评论区有人讨论技术细节 |
| W3 | 场景文 | 《iOS 真机抓包，5 分钟从零到看到请求》配 GIF/短视频 | 少数派 / 即刻 / X 发布，收藏 > 点赞（说明真在用） |
| W4 | 交叉 | Show HN、r/iOSProgramming、awesome-* 列表 PR、公司内部全员试用 | 出现第一条外部用户提的 issue |

节奏纪律：**一周只发一个渠道重点**。同时铺 5 个渠道的结果是每个都做不透，且没有精力回评论。

## 4. 选题库（直接能写，按顺序消耗）

1. HTTP/2 在 MITM 里为什么会被静默降级
2. 客户端握手还没开始就断开时，Node 会悄悄吞掉这个 EOF
3. 为什么抓包工具的「应用名」经常是错的
4. 动态签证书的 397 天有效期是怎么来的（Apple 的规矩）
5. 一次真实的排障：某个域名怎么都解不开，最后发现是证书固定
6. 用 3 行配置把接口「变慢 3 秒」—— 弱网模拟到底该模拟什么
7. 抓包工具自己怎么测自己：29 套自检是怎么长出来的
8. 为什么我不给这个工具做全家桶
9. 从 issue 到发版：一个人维护开源项目的自动化边界
10. 抓包时的隐私红线：哪些数据永远不该贴到公开 issue 里

> 第 7、9 篇是「元内容」——写开发过程本身，这类内容在开发者社区的分发效率往往高于功能教程。

## 5. 反馈漏斗

四层，一层比一层窄，但都能独立成立：

```
应用内「反馈与建议」→ GitHub Issue Forms → 标签流转 → 发版说明回指提出者
```

- **入口**：更多 ⋯ → 反馈与建议（直达 issue 选择页，外链走系统浏览器）
- **模板**：`bug.yml` 强制收版本 / 平台 / 复现；`feature.yml` 只要场景，不要方案
- **门槛**：不想公开流量的用户，不给「诊断包」也能提 —— 版本 + 平台 + 失败域名就够复现
- **闭环**：`needs-triage → accepted → shipped`，发版说明写「来自 @xxx 的反馈」

标签约定：

| 标签 | 谁打 | 含义 |
| --- | --- | --- |
| `needs-triage` | 模板自动 | 待确认 |
| `needs-info` | 分流脚本 | 缺复现信息，已追问 |
| `P0`–`P3` | 分流脚本 | 阻塞无绕过 / 阻塞有绕过 / 影响效率 / 锦上添花 |
| `accepted` | 人工 | 确认要做 |
| `shipped` | 发版时 | 已进版本，@ 提出者 |

## 6. 飞轮四级（AI 自动化边界）

| 级别 | 做什么 | 权限 | 准入条件 |
| --- | --- | --- | --- |
| **L0** | 分类打标 + 追问缺失信息 | 只读代码，写 issue | 已上线（`.github/workflows/triage.yml`） |
| **L1** | 生成复现步骤 / 自检用例草稿 | 只写 `tools/`，不合并 | issue 累计 20+，类型分布稳定 |
| **L2** | 起草实现 PR | 写 `src/ public/ tools/`，全套自检必须绿 | 同类 issue 有 3 次以上成功先例 |
| **L3** | 自动打 tag 发版 | 写发布流程 | 暂不做 |

**写死的护栏**（`tools/check-repo-meta.js` 会校验，改坏了自检就红）：

1. 分流 workflow 只能拿 `issues: write`，不得有 `contents: write` / `pull-requests: write`
2. 分流脚本里不允许出现 `git push` / `git commit` / `gh pr create`
3. 未配置密钥时整条链路静默跳过，绝不让用户看到机器人报错
4. AI 永远不能自己 merge，也不能碰发版与签名流程

## 7. 度量与判定

只看四个数，每周记一次：

| 指标 | 说明 | 健康信号 |
| --- | --- | --- |
| 下载 → 首次成功抓包 | 装完之后能不能用起来 | 首屏文档改完后应明显上升 |
| issue 来源分布 | 内部 / 外部 / 自己发现 | 外部占比上升才算推广有效 |
| issue → 首响时间 | 有没有人理 | < 24h |
| issue → shipped 周期 | 飞轮转速 | 中位数 < 2 周 |

**该刹车的情况**：外部 issue 大多是「装不上」，说明文档/签名问题在挡人，先修地基再推广（macOS 未签名包是当前最大漏斗口，公证值得尽早做）。

## 8. 明确不做

- 不做功能对标清单（跟着别人加功能会一直被动）
- 不做付费/授权体系（现阶段目标是用户量和使用深度，不是收入）
- 不在多个平台同步刷同一篇稿（会被判为搬运，且分散回复精力）
- 不为了 issue 数量做激励（会灌水，污染需求排序依据）
